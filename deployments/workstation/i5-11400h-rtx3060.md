# Intel i5-11400H + RTX 3060 Laptop — llama.cpp runbook

A worked, measured example of the generic [workstation](README.md) checklist on
a laptop with 6 GB of VRAM and 38 GB of RAM. Reproduces an OpenAI-compatible
endpoint on loopback two ways — a CUDA source build and the upstream Docker
image — and records what differs between them.

This host was profiled in the roadmap's *Host note, 2026-08-23* before any
model was served. This runbook is the follow-up that serves one. Results from
this runbook are recorded under
[`benchmarks/2026-08-23-qwen3-coder-30b-cuda-moe/`](../../benchmarks/2026-08-23-qwen3-coder-30b-cuda-moe/result.md)
and, for the agent clients,
[`benchmarks/2026-08-24-qwen3-coder-30b-agent-clients/`](../../benchmarks/2026-08-24-qwen3-coder-30b-agent-clients/result.md).

Unlike the [Ryzen 7 5700U runbook](ryzen-5700u-cpu-only.md), the binding
constraint here is VRAM rather than CPU. The regime being exercised is MoE
hybrid offload: attention, embeddings, and KV on the GPU, expert tensors in
system RAM.

## 1. Hardware baseline

Measured 2026-08-23:

| Property | Value |
| --- | --- |
| CPU | Intel i5-11400H, 6 cores / 12 threads, Tiger Lake-H |
| Vector ISA | AVX-512 with VNNI; no AMX, no `avx512_bf16` |
| GPU | RTX 3060 Laptop, 6144 MiB, sm_86, 80 W TGP |
| VRAM free | 5250 MiB at idle; ~580 MiB held by the desktop session |
| RAM | 38 GB total, 33 GB available |
| Swap | 37 GB |
| Disk | 324 GB free |
| OS / kernel | Ubuntu 24.04.4 LTS, 7.0.0-28-generic |
| Driver | 580.173.02, CUDA 13 capable |
| `nvcc` | 12.0.140, from the `nvidia-cuda-toolkit` apt package |
| Docker | 29.7.1, `nvidia` runtime registered |

Collect the same values with:

```bash
lscpu | grep -E 'Model name|^CPU\(s\)|Core\(s\)'
grep -o -m1 -E 'avx512[a-z0-9_]*' /proc/cpuinfo | sort -u
free -g
nvidia-smi --query-gpu=name,memory.total,memory.used --format=csv
nvcc --version | tail -2
```

### Consequences

Full GPU offload is bounded by roughly 5.2 GB of weights plus KV cache. A
30B-class model does not fit that budget, but a *sparse* one does not need to:
with `--n-cpu-moe`, decode cost scales with **active** parameters rather than
total. `qwen3-coder:30b` is 30.5B total at ~3.3B active.

vLLM and SGLang remain unusable here for the reasons the roadmap records: 6 GB
does not hold an unquantized 7B, and while AVX-512 with VNNI means the vLLM CPU
backend would now build, the absence of AMX and `avx512_bf16` leaves it behind
llama.cpp.

## 2. Choosing between the two approaches

Both work on this host and both were measured. They are not far apart.

| | Source build | Docker image |
| --- | --- | --- |
| Setup | ~13 min compile | 3.61 GB pull |
| Tracks upstream | Yes, any commit | Lags; image was build 8953 |
| CPU backend | `-march=native` | `libggml-cpu-icelake.so` |
| `--load-mode` | Yes | No — use `--no-mmap` |
| Prefill @ 5,532 tok | 272.1 tok/s | 274.5 tok/s |
| Toolchain risk | Host `nvcc`/gcc pairing | None |

Prefer the **source build** when the measurement must be reproducible against a
named commit, or when a flag lands upstream faster than the image rebuilds —
`--load-mode` is exactly that case. Prefer **Docker** when the host toolchain is
the obstacle, or when the endpoint has to be reproduced on another machine
without a compiler.

A common assumption does not hold here: the image does **not** ship a
lowest-common-denominator CPU backend. llama.cpp builds several CPU variants and
dispatches at runtime, and on this host the container selects
`libggml-cpu-icelake.so`, which carries AVX-512 and VNNI. Measured prefill was
within noise of the `-march=native` build. Do not choose the source build on the
expectation of a large CPU-side win; choose it for version control over the
binary.

Only one server can hold the GPU at a time. Stop one before starting the other.

## 3a. Approach A — build from source

`libcurl4-openssl-dev` is required for `-hf` downloads.

```bash
sudo apt install -y build-essential cmake git libcurl4-openssl-dev
git clone --depth 1 https://github.com/ggml-org/llama.cpp.git ~/repos/llama.cpp
cd ~/repos/llama.cpp
cmake -B build \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_NATIVE=ON \
  -DGGML_CUDA=ON \
  -DCMAKE_CUDA_ARCHITECTURES=86 \
  -DLLAMA_CURL=ON
cmake --build build --target llama-server llama-cli llama-bench -j "$(nproc)"
```

`-DGGML_CUDA=ON` is the line the Ryzen runbook omits, and the reason its CMake
invocation cannot be copied here. `-DCMAKE_CUDA_ARCHITECTURES=86` restricts
codegen to this GPU's sm_86 and keeps the build near 13 minutes; drop it only if
the binaries must run on another card.

Verify the CUDA backend is present rather than assuming it:

```bash
~/repos/llama.cpp/build/bin/llama-server --list-devices
# expect: CUDA0: NVIDIA GeForce RTX 3060 Laptop GPU (5804 MiB, 5250 MiB free)
export LLAMA_CPP_PATH="$HOME/repos/llama.cpp/build/bin"
```

### The `nvcc` 12.0 / gcc 13 pairing

Ubuntu 24.04 defaults to gcc 13, and CUDA 12.0 upstream refuses host compilers
newer than 12.1. This does **not** block the build: the apt-packaged toolkit
selects gcc-12 automatically, and CMake reports `CUDA host compiler is GNU
12.4.0`. No NVIDIA repository and no manual `CMAKE_CUDA_HOST_COMPILER` are
needed.

Confirm the pairing works before starting a long compile:

```bash
printf '#include <cstdio>\n__global__ void k(){}\nint main(){k<<<1,1>>>();printf("ok\\n");}\n' > /tmp/t.cu
nvcc -arch=sm_86 /tmp/t.cu -o /tmp/t && /tmp/t   # expect: ok
```

llama.cpp sets no CUDA minimum above 11.6, so the 12.0 toolkit is in range.

## 3b. Approach B — Docker image

The NVIDIA Container Toolkit and the `nvidia` runtime were already present on
this host; `docker info` lists `nvidia` under runtimes. Nothing was installed
for this path.

```bash
docker pull ghcr.io/ggml-org/llama.cpp:server-cuda
docker run --rm --gpus all \
  --entrypoint /app/llama-server \
  ghcr.io/ggml-org/llama.cpp:server-cuda --list-devices
```

The image's default entrypoint is already `llama-server`, so `--entrypoint` is
needed only for one-off introspection like `--version` or `--list-devices`.

The container's driver requirement is satisfied in the forward direction: a
CUDA 12.x container runs against this 580.173 / CUDA 13 driver.

## 4. Serve

Both approaches read the same GGUF. Ollama's blobs are bare GGUF files and are
world-readable, so `llama-server -m` loads them directly and no second 18.6 GB
copy is needed:

```bash
find /usr/share/ollama/.ollama/models -name 'sha256-*' -size +1G -exec ls -lh {} \;
```

On this host `sha256-1194192c…` is `qwen3-coder:30b` (Q4_K_M, 18.6 GB) and
`sha256-b112e727…` is `gpt-oss:20b` (MXFP4, 13.8 GB). Confirm the mapping from
the manifests under `manifests/registry.ollama.ai/library/` rather than by size
alone.

### Source build

```bash
BLOB=/usr/share/ollama/.ollama/models/blobs/sha256-1194192cf2a187eb02722edcc3f77b11d21f537048ce04b67ccf8ba78863006a
~/repos/llama.cpp/build/bin/llama-server \
  -m "$BLOB" \
  --alias qwen3-coder-30b \
  -ngl 99 --n-cpu-moe 42 --load-mode none \
  --ctx-size 32768 --cache-type-k q8_0 --cache-type-v q8_0 \
  --flash-attn on --threads 6 --parallel 1 --cache-reuse 256 \
  --host 127.0.0.1 --port 8080
```

### Docker

```bash
docker run -d --name llama-cuda --gpus all \
  -v /usr/share/ollama/.ollama/models/blobs:/models:ro \
  -p 127.0.0.1:8081:8080 \
  ghcr.io/ggml-org/llama.cpp:server-cuda \
  -m /models/sha256-1194192cf2a187eb02722edcc3f77b11d21f537048ce04b67ccf8ba78863006a \
  --alias qwen3-coder-30b \
  -ngl 99 --n-cpu-moe 42 --no-mmap \
  --ctx-size 32768 -ctk q8_0 -ctv q8_0 \
  --flash-attn on --threads 6 --parallel 1 --cache-reuse 256 \
  --host 0.0.0.0 --port 8080
```

The blob directory is mounted `:ro`; the container never needs to write it.

`--host 0.0.0.0` inside the container is **not** a loopback regression. The
container has its own network namespace, and `-p 127.0.0.1:8081:8080` is what
binds the published port to the host's loopback. Publishing as `-p 8081:8080`
would expose the endpoint on every host interface — that is the mistake to
avoid, not the `0.0.0.0` argument.

### Flag rationale for this host

- `-ngl 99` places every layer on the GPU, then `--n-cpu-moe 42` moves the
  expert tensors of the first 42 layers back to CPU. The two are used together,
  not as alternatives: attention, embeddings, norms, and KV stay on the GPU
  while the bulk of the weights sit in RAM;
- `--n-cpu-moe 42` rather than `--cpu-moe` is the tuned value. `--cpu-moe`
  keeps all 48 layers' experts on CPU and left 2.9 GB of VRAM unused. Raising
  the offload to the last 6 layers filled VRAM to 5516 MiB and bought 37% of
  prefill. Tune this number per model — it is a memory fit, not a constant;
- `--load-mode none` (source) / `--no-mmap` (Docker) is prompted by the server's
  own warning, `tensor overrides to CPU are used with mmap enabled - consider
  using --load-mode none for better performance`. With 33 GB available the
  18.6 GB of weights are resident rather than mapped;
- `--threads 6` matches physical cores; SMT threads reduce throughput;
- `--cache-type-k/v q8_0` halves the KV cache, and requires `--flash-attn on` —
  the server exits with `quantized V cache requires flash_attn to be enabled`
  otherwise;
- `--alias` fixes the id returned by `/v1/models` so client configuration does
  not depend on the blob digest;
- `--parallel 1` because there is no VRAM headroom for concurrent slots;
- `--jinja` is **not** passed: it is already the default in current builds. It
  was required explicitly on the Ryzen host.

### Variant: 65536 context for Hermes

Hermes Agent refuses any model reporting under 64,000 tokens. Qwen3-Coder-30B
is trained to 262144, so raising the window is honest here rather than an
overstatement. The KV cache roughly doubles to ~3.4 GB, which must be taken
back from the expert tensors on the GPU.

This is the configuration the four agent clients were verified against, so it
is given in full rather than as a diff:

```bash
docker run -d --name llama-cuda --gpus all \
  -v /usr/share/ollama/.ollama/models/blobs:/models:ro \
  -p 127.0.0.1:8080:8080 \
  ghcr.io/ggml-org/llama.cpp:server-cuda \
  -m /models/sha256-1194192cf2a187eb02722edcc3f77b11d21f537048ce04b67ccf8ba78863006a \
  --alias qwen3-coder-30b \
  -ngl 99 --n-cpu-moe 46 --no-mmap \
  --ctx-size 65536 -ctk q8_0 -ctv q8_0 \
  --flash-attn on --threads 6 --parallel 1 --cache-reuse 256 \
  --host 0.0.0.0 --port 8080
```

For the source build, substitute the binary and `--load-mode none` for
`--no-mmap`, and bind `--host 127.0.0.1` directly.

`--n-cpu-moe 46` rather than 42, leaving 5692 MiB of 6144 in use. Measured cost
against the 32768 configuration: prefill 272 → 239 tok/s, decode 11.3 → 9.2
tok/s at ~5.5k context. Use 32768 when Hermes is not in play. Results are in
[`benchmarks/2026-08-24-qwen3-coder-30b-agent-clients/`][agents-result].

## 5. Validate

```bash
curl -s http://127.0.0.1:8080/v1/models | python3 -m json.tool
curl -s http://127.0.0.1:8080/props |
  python3 -c 'import json,sys; print(json.load(sys.stdin)["default_generation_settings"]["n_ctx"])'
```

Then screen tool calls before wiring any agent, per the roadmap's rule that
capability is model-specific and settled by an isolated request:

```bash
curl -s http://127.0.0.1:8080/v1/chat/completions -H 'Content-Type: application/json' -d '{
 "model":"qwen3-coder-30b",
 "messages":[{"role":"user","content":"What is the weather in Paris right now?"}],
 "tools":[{"type":"function","function":{"name":"get_weather",
   "parameters":{"type":"object","properties":{"city":{"type":"string"}},"required":["city"]}}}],
 "temperature":0}'
```

Expect `finish_reason: tool_calls` and `{"city":"Paris"}`.

## 6. Measured results

Single samples on an identical 5,532-token prompt, `temperature: 0`, both
servers using the tuned configuration above.

| Configuration | Prefill | Decode @ 5.5k ctx |
| --- | --- | --- |
| Source, `--cpu-moe`, mmap | 199.0 tok/s | 10.9 tok/s |
| Source, `--n-cpu-moe 42`, `--load-mode none` | 272.1 tok/s | 11.3 tok/s |
| Docker, `--n-cpu-moe 42`, `--no-mmap` | 274.5 tok/s | 10.2 tok/s |

VRAM: 3250 MiB under `--cpu-moe`, 5516 MiB under `--n-cpu-moe 42`, for both
approaches. Model load took 28 s (source) and 33 s (Docker) with a warm page
cache.

Decode depends on KV depth. Against short prompts the same Docker server
measured 13.8 / 13.4 / 13.9 tok/s across three runs — roughly 4% spread, and
noticeably faster than the ~10 tok/s seen once 5.5k tokens are resident.
Quote decode figures with the context depth attached or they are not
comparable.

The source-versus-Docker decode gap (11.3 against 10.2) rests on one sample
each and is close enough to the observed spread that it should not be read as a
real difference without repeated runs.

### Interpretation

Prefill at 272 tok/s is roughly 5x the Ryzen host's ~49 tok/s, which shrinks
OpenCode's 7,876-token cold start from about 161 s to about 29 s. That is a
large improvement and it does **not** reach the roadmap's estimate of
1,000-2,000 tok/s. The estimate was written for a 4B-class model held entirely
in VRAM; in the MoE hybrid regime prefill remains bound by CPU expert compute.
The prompt-size intervention is therefore only partly demonstrated here, and
the full-GPU Gemma 4 E4B slot is still the configuration that would test the
estimate as written.

## 7. Connect a client

Two rules govern every client below. The model key must equal the server's
`--alias`, which is what `/v1/models` returns — not the blob digest and not the
upstream model name. The client's declared context limit must equal
`--ctx-size`; an overstated limit is not rejected, it makes the client pack
prompts that are silently cut before the model sees them.

Port 8080 throughout. The 8081 used earlier on this page exists only to run the
Docker container beside the source build during a comparison; only one server
can hold the GPU, so there is no reason to keep two ports in normal use.

All four clients were verified against this host on 2026-08-26 and are recorded
in [`benchmarks/2026-08-26-agent-client-prompt-sizes/`][agents-2026-08-26].

| Client | Config file | Select with |
| --- | --- | --- |
| OpenCode | `~/.config/opencode/opencode.json` | `--model llama.cpp/qwen3-coder-30b` |
| Kilo | `~/.config/kilo/kilo.jsonc` | `--model llama.cpp/qwen3-coder-30b` |
| Pi | `~/.pi/agent/models.json` | `--provider local --model qwen3-coder-30b` |
| Hermes | `~/.hermes/config.yaml` | `--provider local -m qwen3-coder-30b` |

Each is selected per run, so none of them repoints a configured default to the
local endpoint.

### OpenCode and Kilo

Kilo is an OpenCode fork and takes the same provider schema. Merge this under
the top-level `provider` key, keeping anything already there — providers merge
by key, so an added block leaves existing ones intact:

```json
"llama.cpp": {
  "npm": "@ai-sdk/openai-compatible",
  "name": "llama-server (local)",
  "options": { "baseURL": "http://127.0.0.1:8080/v1", "apiKey": "dummy" },
  "models": {
    "qwen3-coder-30b": {
      "name": "Qwen3-Coder 30B-A3B (local)",
      "limit": { "context": 65536, "output": 8192 }
    }
  }
}
```

`apiKey` is required because the OpenAI client sends the header; the server
ignores its value, having been started without `--api-key`. Verify by anchoring
the grep to the provider key:

```bash
opencode models | grep '^llama\.cpp/'
```

A bare `grep llama` is not a check. The model catalog carries around thirty
Llama-family entries from hosted providers, so it matches whether or not the
local provider loaded.

### Pi

```json
{
  "providers": {
    "local": {
      "baseUrl": "http://127.0.0.1:8080/v1",
      "api": "openai-completions",
      "apiKey": "none",
      "models": [{ "id": "qwen3-coder-30b" }]
    }
  }
}
```

`pi --list-models local` reports the context as 128K. That is Pi's own catalog
default rather than a value read from the endpoint; the served window is
whatever `--ctx-size` was passed.

### Hermes

Hermes needs `--ctx-size 65536` or more — see the variant above — and its
`--provider` flag has changed shape three times across versions. On 0.20.5:

```yaml
providers:
  local:
    base_url: "http://127.0.0.1:8080/v1"
    api_key: "none"
```

```bash
hermes chat -q "Reply with exactly the word: ready" \
  --provider local -m qwen3-coder-30b
```

Check `hermes chat --help` against the installed build first; the
[integration page](../../integrations/hermes/) carries the version table and the
profile-based fallback for builds whose `--provider` is a closed enum.

### Expect a slow first turn

Prefill runs at 193-196 tok/s here regardless of client, so time to first token
is set by how large a system prompt the client ships — 25 s for Pi through
113 s for Hermes, measured. Nothing is wrong when a bare greeting takes a
minute; check the server log before changing any setting.

Consecutive runs are much cheaper than the first, because `llama-server`'s slot
cache keeps the common prefix and re-prefills only the diverging tail. Prefer a
TUI session over repeated one-shot `run` invocations.

## 8. Start, stop, and verify

Only one server can hold this GPU, so switching between the source build and
the container — or between the 32768 and 65536 configurations — means stopping
the running one first.

```bash
pkill -f 'llama-server.*--port 8080'   # source build
docker rm -f llama-cuda                # Docker
```

Confirm the resources actually came back rather than assuming they did. A
container that is `Up (healthy)` still holds every megabyte it allocated:

```bash
curl -s -m 3 http://127.0.0.1:8080/v1/models >/dev/null && echo serving || echo down
nvidia-smi --query-gpu=memory.used,memory.total --format=csv,noheader
free -h | head -2
```

On this host an idle GPU reads ~439 MiB — the desktop session and an unrelated
KServe runtime — not zero. Anything above that after a stop means something is
still resident. Expect roughly 18.6 GB of RAM to be released as well, since
`--no-mmap` holds the weights as anonymous memory rather than page cache.

To bring the endpoint back, re-run the serve command from step 4 or the 65536
variant above. The client configurations in step 7 need no changes; they only
require a server on port 8080 answering to the alias `qwen3-coder-30b`.

### Reading `/v1/models`

The response carries two arrays. `models[]` describes each model with a `name`
key, while `data[]` is the OpenAI-compatible view keyed by `id` and is where
the useful metadata sits:

```bash
curl -s http://127.0.0.1:8080/v1/models |
  python3 -c 'import json,sys; m=json.load(sys.stdin)["data"][0];
print(m["id"], m["meta"]["n_ctx"], m["meta"]["ftype"])'
```

Indexing `id` on `models[]` returns a `KeyError` and looks exactly like an
endpoint that is down. Read `n_ctx` from here to confirm the served window
matches what the clients declare.

## Known issues on this host

**`ollama show qwen3-coder:30b` advertises `completion` only, without
`tools`.** Served through `llama-server`, the model emits correct tool calls
anyway — verified on both the source build and the Docker image. As with the
Qwen2.5-Coder record, that flag describes Ollama's bundled template rather than
the weights, but here the outcome is the reverse: the capability is present and
only Ollama's own serving path hides it. This model is safe to wire to an agent;
`gpt-oss:20b` remains unscreened.

**The Docker image lags upstream.** The pulled image reported build 8953
(`434b2a1ff`) while a same-day clone of master built `95b8e33`. The gap is not
cosmetic: the image has no `--load-mode`, so the mmap workaround must be spelled
`--no-mmap`. Check `--help` in the container before copying a flag from a
source-build command, and record the image build in any result that uses it.

**`failed to fit params to free device memory: n_gpu_layers already set by user
to 99, abort`** appears at startup on both paths. It is llama.cpp declining to
auto-fit because `-ngl` was set explicitly, not an allocation failure. The
server continues and loads normally.

**`--n-cpu-moe` is model-specific.** The value 42 is a fit for this GGUF at
32768 context with a q8_0 KV cache. Changing the model, the quantization, the
context size, or the KV cache type invalidates it. Retune by watching
`nvidia-smi` and lowering the number until VRAM is nearly full without an
allocation failure.

**Only one server can hold the GPU.** The source build and the container both
claim ~5516 MiB. Starting the second while the first runs will fail to allocate.
